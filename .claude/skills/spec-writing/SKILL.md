# 사양서 작성 (Spec Writing)

사양서는 `docs/SRS.md` 한 파일로 관리한다. 이 파일의 표는 `traceability` 스킬의 스크립트가 기계적으로 읽으므로 **아래 형식을 반드시 지킨다.**

## 1. 요구사항 계층

| 계층 | ID 형식 | 관점 | 예 |
|---|---|---|---|
| 사용자 요구사항 (UR) | `UR-001` | 플레이어/사용자가 원하는 것. 구현 용어 없이 기술 | 같은 캐릭터 두 개가 닿으면 합쳐져야 한다 |
| 소프트웨어 요구사항 (SR) | `SR-001` | 소프트웨어가 해야 하는 일. 수치·조건이 들어가 시험 가능해야 함 | 같은 단계 두 캐릭터가 접촉하면 둘을 제거하고 중점에 다음 단계 1개를 생성한다 |

- ID 는 3자리 0 채움, **재사용 금지**. 삭제된 요구사항의 ID 는 비워 두고 "삭제" 로 표기한다.
- 모든 SR 은 1개 이상의 UR 에서 파생되어야 한다 (상위 UR 없는 SR = 고아, 금지).
- 모든 UR 은 1개 이상의 SR 로 구체화되어야 한다.

## 2. 문장 규칙

- 하나의 요구사항 = 하나의 시험 가능한 행위. "그리고"로 무관한 기능을 묶지 않는다.
- SR 은 측정 가능한 값(시간 ms, 크기 px, 개수, 점수식)을 포함한다. "빠르게", "적절히" 금지.
- 서술어: UR 은 "~할 수 있어야 한다", SR 은 "~한다 / ~해야 한다".
- 기존 코드에서 역으로 추출할 때는 코드의 실제 상수를 그대로 쓰고, 코드와 다르게 **바라는 동작**을 적었다면 그 SR 은 시험에서 실패할 수 있음을 인지한다 (결함으로 보고).

## 3. 표 형식 (파싱 규칙)

UR 표 — 첫 열이 `UR-nnn` 인 행만 요구사항으로 인식:

```markdown
| ID | 사용자 요구사항 | 우선순위 |
|---|---|---|
| UR-001 | 플레이어는 … 할 수 있어야 한다. | 필수 |
```

SR 표 — 첫 열이 `SR-nnn` 인 행만 인식. **열 순서 고정**:

```markdown
| ID | 소프트웨어 요구사항 | 상위 UR | 구현 위치 |
|---|---|---|---|
| SR-001 | … 한다. | UR-002, UR-004 | `RADII`, `drop()` |
```

- `상위 UR`: 쉼표로 구분한 UR ID 목록.
- `구현 위치`: 소스(`chiikawa-merge.html`)에 실제로 존재하는 식별자를 백틱으로 적는다. 함수는 `name()`, 상수/변수/문자열은 그대로. **줄 번호는 적지 않는다** — 줄 번호는 추적성 스크립트가 매번 소스에서 계산해 링크로 만든다 (코드 수정 시 어긋나지 않도록).
- 셀 안에 `|` 를 쓰지 않는다.

## 4. 사양서 목차

1. 개요 (목적, 범위, 대상 버전/커밋, 용어)
2. 시스템 개요 (구성, 화면 배치, 주요 상수)
3. 사용자 요구사항 (UR 표)
4. 소프트웨어 요구사항 (SR 표, 기능 영역별 소제목 가능 — 표가 여러 개여도 됨)
5. 제약 사항 / 가정
6. 추적성 — `traceability-matrix.md` 링크 (사양서에 TC 를 직접 적지 않는다. TC↔SR 매핑의 원본은 `docs/test-cases.md`)
7. 문서 이력

## 5. 변경 절차

1. UR/SR 을 추가·수정한다 (위 형식 준수).
2. `test-case-writing` 스킬로 해당 SR 을 검증하는 TC 를 추가·수정한다.
3. `traceability` 스킬로 테스트 실행 → 추적성 매트릭스를 재생성하고 위반 사항이 없는지 확인한다.
4. 문서 이력에 변경 내용을 한 줄 추가한다.
